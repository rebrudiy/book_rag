# Эксперимент: фрагменты как диапазоны текста раздела

На неизменяемом снимке 1 308 книжных записей проверено, можно ли убрать
дублирующий `passages.text`, сохранив точные цитаты как
`sections.text[start:end]`. **Это только экспериментальная копия. Текущие
Library и embedding consumers читают `passages.text` и несовместимы с пустым
sentinel. Ни производственная база, ни схема, ни код приложения не изменены.**

Результат 15 ноября 2026 года: база уменьшилась с **1 594 347 520** до
**940 126 208 байт**, экономия **654 221 312 байт / 41,03%**. Это 623,91 МиБ
в данном снимке, а не прогноз размера всей библиотеки или числа уникальных книг.
Артефакты оригиналов, модели и векторы этим изменением не уменьшаются.

Исходник: `data/snapshots/library1308-v1/library.sqlite3`, SHA-256
`2d77675ba2a68f63e25f507355272e3206db8f9abbe959f326cea96f774939f0`.
Он открыт SQLite с `mode=ro&immutable=1`, `query_only=ON`; `Library` не создаётся.
SHA, inode/размер/mtime/ctime проверены до и после; исходник остался неизменным.
Запись и VACUUM выполнялись только в новой собственной копии
`data/benchmarks/span-storage1308-v1/library.sqlite3`.

## Что проверено полностью

До удаления дубликата и после него проверены **все 445 466 фрагментов**:

- `book_id` существует и совпадает с книгой раздела;
- `start/end` — целые и лежат внутри исходного Unicode-текста;
- срез Python совпадает с сохранённым текстом до удаления;
- UTF-8 SHA-256 среза совпадает с `passages.sha256`;
- ID, книга, раздел, диапазон, SHA и итоговый текст дают прежние агрегатные хеши.

Всего восстановлено 532 605 481 символ / 538 653 017 байт UTF-8;
275 696 фрагментов содержат не-ASCII символы. Все 59 691 раздел сохранены.
После `UPDATE passages SET text=''` и VACUUM схема `NOT NULL` не менялась,
все `passages.text` пусты, значения ID и диапазонов прежние.

Логические fingerprints всех остальных таблиц совпали, включая `books`,
`sections`, `book_metadata`, `section_roles`, pipeline metadata и четыре
contentless FTS shadow tables. Команды FTS optimize/rebuild/delete не вызывались.
Foreign-key check не обнаружил ошибок. Восемь запросов дали прежние ID, BM25
scores, метаданные и полные тексты первых 20 результатов при восстановлении
через SQL `substr`. Для равных scores явно используется tie-break по `p.id`.

Проверка `dbstat` отделяет эффект удаления текстов от уборки старого freelist:
в исходнике и результате **0 свободных страниц**. Физический B-tree `passages`
уменьшился с 698 716 160 до 44 498 944 байт; остальные B-tree по `dbstat` имеют
прежний размер. Это объясняет 654 217 216 байт экономии; ещё 4 096 байт приходятся
на разницу общей файловой разметки вне этих B-tree. Размер `sections` неизменен:
572 129 280 байт. Временные файлы VACUUM использовались только рядом с копией.

## Время и память

| Показатель | Измерение |
| --- | ---: |
| Полная проверка исходных spans | 5,83 с |
| Полное восстановление и проверка после очистки | 5,96 с |
| UPDATE копии / VACUUM копии | 5,48 / 10,81 с |
| Весь запуск, включая копирование, fingerprints и latency probes | 90,76 с |
| Peak RSS всего процесса | 200 753 152 байта, около 191,45 МиБ |
| SQLite cache | 32 МиБ на соединение |
| Бюджет Python LRU | 16 МиБ строк + ограничение 128 разделов |
| Измеренный пик строк LRU | 16 775 175 байт |

Для **254 реальных passage ID** выбраны начала/середины/концы коротких и длинных
разделов, примеры DE/EN/FR/RU и детерминированная случайная выборка. Все три
метода вернули одинаковые `(id,text)`:

| Получение 254 фрагментов | Медиана 5 запусков | Максимум |
| --- | ---: | ---: |
| Сохранённый `p.text` | 1,53 мс | 16,22 мс |
| SQL `substr(s.text,start+1,end-start)` | 32,16 мс | 35,90 мс |
| Python slicing с LRU | 15,57 мс | 16,42 мс |

Это локальные последовательные измерения с тёплыми кэшами, не cold-disk
benchmark. Для восьми полных BM25 probes SQL-результаты иногда быстрее на меньшем
файле, иногда медленнее; это не доказывает ускорение production-поиска. SQL
`substr` проверен на ограниченных ID и query results; **для всех** фрагментов
проверен именно Python slicing. LRU budget считает строки через `getsizeof`, а
не всю память Python/SQLite; общий RSS указан отдельно.

Перед стартом было свободно 17 315 454 976 байт, проверяемый минимальный запас —
9 078 009 856 байт: 4 ГиБ резерва + тройной размер исходника под копию, journal и
VACUUM. Перед VACUUM запас проверен снова; после запуска свободно
16 348 106 752 байта. Существующий FTS benchmark и его результаты не менялись.

## Повторение и дальнейшая работа

```sh
.venv/bin/python scripts/benchmark_span_storage.py \
  --source data/snapshots/library1308-v1/library.sqlite3 \
  --output-dir data/benchmarks/span-storage1308-v2 \
  --report experiments/span-storage-v2.json
```

Каталог и report должны быть новыми; скрипт отказывается перезаписывать прежние
результаты и требует размещения копии внутри `data/benchmarks`. Машинный отчёт
текущего запуска — `experiments/span-storage-v1.json`, только метаданные, хеши,
ID/scores и измерения. Полные raw/reconstructed query outputs и sample text
остаются в игнорируемом `data/benchmarks/span-storage1308-v1/`.

Следующая задача перед возможной интеграцией — отдельная реализация общего
получения passage text для всех consumers, включая поиск, integrity, экспорт,
saved provenance и embeddings, с проверкой совместимости старых баз и миграции.
Этот эксперимент не включает миграцию, не удаляет `passages.text` в настоящей
библиотеке и не разрешает запускать нынешний production-код на sentinel-копии.
